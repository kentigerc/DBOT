# NetoAcademy initial offline load test — 6 November 2026

The test passed with 1, 5, 10 and 20 concurrent simulated server trading accounts. This is an initial performance baseline, **not a verified production user limit** for Render.

| Active simulated accounts | Live simulated feeds | Peak process RAM | CPU (one core = 100%) | HTTP polling p95 | Fake purchases | HTTP failures |
| ------------------------- | -------------------- | ---------------- | --------------------- | ---------------- | -------------- | ------------- |
| 1                         | 20                   | 83.5 MB          | 2.6%                  | 6.7 ms           | 6              | 0             |
| 5                         | 100                  | 105.7 MB         | 4.5%                  | 12.8 ms          | 24             | 0             |
| 10                        | 200                  | 115.7 MB         | 8.3%                  | 15.5 ms          | 52             | 0             |
| 20                        | 400                  | 138.4 MB         | 13.1%                 | 31.9 ms          | 101            | 0             |

All accounts stayed active, all feeds loaded, and all fake purchases settled. Each run lasted about 21 seconds including initialization, with 20 one-second market feeds per account and one HTTP status poll per account per second. These are short bursts, not a long-running soak test. The 20-account case processed 8,000 ticks and 101 fake purchases/settlements. The measured process ran Node v20.20.1 on Linux with a four-CPU cgroup quota and a 32 GiB memory limit. V8 old space was capped at 256 MiB, which does not impose a 512 MiB total RAM limit or simulate a half-CPU server.

## What was exercised

- The actual compiled trading engine, using the current Even/Odd strategy and recovery logic.
- Concurrent market initialization, rolling 1,000-tick samples, signal evaluation and session polling through the real loopback HTTP analysis handler.
- Fake balances, quotes, buys, wins/losses and contract settlement. No funds, real accounts or provider credentials were used.
- The actual synchronous file journal, isolated to a temporary directory removed after the run.
- Event-loop delay, CPU, sampled process RSS, request latency, failures and unexpected strategy stops.

The fake feed emits at one tick per second on every market. Fake contracts settle immediately when monitored, so contract pacing differs from real two-tick contracts. The load generator, mock broker and server share one measured process, so client/mock overhead is included.

## What this does not establish

The test does not measure Deriv latency, API quotas, real TLS/WebSocket traffic, PostgreSQL analytics, static asset bandwidth, browser-side XML execution, OAuth services, cold starts or Render disk/scheduler performance. It does not reproduce the exact production server's full memory footprint. A provider outage can still stop trading regardless of CPU or RAM.

The current Render plan is not changed by running this test. Use a small controlled pilot on the intended plan and observe Render CPU/RAM and connection stability before raising concurrency. A production capacity claim needs a longer staging test on matching compute, representative trading tools, status polling from multiple devices and the real database. Do not run a stress test against a service handling real-money trades.

## Reproduce offline

```sh
npm run test:load
```

Or use explicit bounds and save the report:

```sh
npm run build:strategy
node scripts/load-test.cjs --users=1,5,10,20 --markets=20 --seconds=20 --output=/tmp/neto-load-results.json
```

Each scenario runs in a fresh child process. The script binds loopback only and injects its fake broker; it has no live Deriv or Render target option. It does not place orders or change hosting plans.
